# CodexGraph released-skill reliability gap analysis

## Scope and verdict rule

This review is against the released tree at `skills/codex-graph/` in v0.5.6: `SKILL.md`, all six Markdown references (`progressive-complexity.md`, `topology-library.md`, `code-mode-script-patterns.md`, `task-lifecycle.md`, `reference-seeds.md`, and `self-testing.md`), and the complete `testcases/` bundle (README, catalog, six cases, and the offline harness). The findings below classify the *whole reliability area*, not whether an adjacent safeguard exists:
For compactness, `SKILL.md:` below means `skills/codex-graph/SKILL.md:`; `references/...:` means `skills/codex-graph/references/...:`. Testcase paths are rooted at `skills/codex-graph/testcases/`.

- **Mandated** means the area is stated as an enforceable contract and the relevant execution shape is required.
- **Partially mandated** means the tree has useful neighboring guardrails, but the failure-specific contract or gate is missing.
- **Absent** means the tree has no contract that requires the area; related status/transport behavior is not counted as a substitute.

The observed mailbox failures are stated only as sanitized categories: delegated archive authority despite a reviewer saying root-only L0; a blocked terminal reported as success while a human decision queue was hidden; shape-only C1–C5 acceptance; archives after truncated batch reads; and an expired verification code archived.

## What the testcase harness does—and does not—prove

The six golden cases are useful regression tripwires for topology and collection mechanics. Their catalog describes root-owned joins, fail-closed lanes, per-node environments, and root publication (`testcases/catalog.json:5-81`), while the README says the harness is offline/static and names the exercised contracts (`testcases/README.md:1-10`, `:45-57`). The checker enforces required node IDs, `Promise.allSettled`, local/worktree markers, read-first/read-after-wait, the item budget, `repairUsed`, `terminalEmitted`, pending setup-resolution markers, and forbidden prompt snippets (`testcases/harness/expectations.js:156-301`, `:304-359`). Its own tests verify that wait-only collection, missing post-wait reads, oversized item budgets, missing terminal guards, over-scoped prompts, and unresolved `clientThreadId` handling fail (`testcases/harness/testcases.test.js:185-280`).

Those checks do **not** execute a worker, inspect a human-facing parent conversation, verify facts against an external source, prove a read is untruncated, classify security-sensitive records, or gate a user-state mutation. Passing the testcase harness is therefore not evidence that any of the five failure-specific gaps is closed.

## Baseline conclusion

The released skill is strong on serialized ownership, bounded task lifecycle, structured evidence envelopes, collection-error forensics, and generic fail-closed validator/tool handling. It is not decision-complete for the mailbox failures: a follow-up reliability specification still needs (a) an authority-bearing/interactive topology decision and root-only mutation boundary, (b) a parent-visible ask/answer continuation loop, (c) fact-level acceptance evidence, (d) a completeness proof before mutation, and (e) typed fail-closed security categories covering verification material and archive policy.
